### HIGH-1 — Stored XSS via receipt upload, leading to session takeover **[VERIFIED]**

`app/api/budget/entries/[entryId]/receipts/route.ts` performs **no MIME-type or content validation** on uploaded files, and `app/api/budget/entries/[entryId]/receipts/[filename]/route.ts` serves them back with the stored content type and `Content-Disposition: inline`.

**Reproduction** (verified end-to-end against the real Blob store):
1. As any member of any club, create an EXPENSE budget entry.
2. `POST /api/budget/entries/<entryId>/receipts` with multipart `files=@payload.html`, part header `Content-Type: text/html`, body `<script>/* attacker JS */</script>`.
3. `put()` is called with no `contentType` option, so `@vercel/blob` derives it from the uploaded `File.type` — i.e. from the attacker's own multipart headers. Confirmed by round-trip: uploaded `File{name:"payload.html", type:"text/html"}`, read back `blob.blob.contentType === "text/html"`.
4. Any club member opening that receipt hits `GET /api/budget/entries/<entryId>/receipts/payload.html`, which responds `Content-Type: text/html` + `Content-Disposition: inline`.

**Impact.** The script executes on the application's own origin. Receipts are shared club artifacts, so a club **Member** can plant one and wait for the club **Admin** (or anyone else) to open it. The payload runs with the victim's Clerk session and can call every API route as them. Because Clerk sessions are per-user and not per-org, a victim who belongs to both a club and the Union Staff org (a student-government member — an entirely normal case for this product) hands the attacker union-level access to the whole institution's approval queues. SVG uploads work identically. Note the union never views receipts today, which is the only thing keeping this from being a direct club→union escalation path by default.

**Suggested fix.** Allowlist content types at upload (`image/png`, `image/jpeg`, `image/webp`, `application/pdf`) and reject everything else; do not trust `File.type` alone — sniff magic bytes. On download, ignore the stored content type and send an allowlisted one, add `Content-Security-Policy: default-src 'none'; sandbox`, `X-Content-Type-Options: nosniff`, and use `Content-Disposition: attachment` for anything that isn't a known-safe image. Serving user files from a separate origin would be the durable fix.

### HIGH-2 — One malformed date permanently breaks a club's Budget and Events pages **[VERIFIED]**

The date validators in `app/api/budget/entries/route.ts:29-31` and `app/api/events/[eventId]/route.ts:44-47` accept any string that produces a non-`NaN` JS `Date`. JS `Date` supports years up to 275760; Postgres `timestamp` accepts them; **but the `pg` driver returns `Invalid Date` when reading such a row back**, and both render paths then call `.toISOString()` on it unguarded.

**Reproduction** (verified against the real database):
1. As any club member: `POST /api/budget/entries` with `{"amount":1,"type":"EXPENSE","date":"+020000-01-01"}`.
2. Validator passes (`Number.isNaN(new Date("+020000-01-01").getTime())` is `false`). Row is written.
3. Reading it back yields `Invalid Date`. `lib/budget-serialize.ts:22` (`entry.date.toISOString()`) throws `RangeError: Invalid time value`.
4. `app/budget/page.tsx` maps **every** entry through `serializeEntry`, so the entire `/budget` page 500s. `GET /api/budget/entries` 500s for the same reason.

Verified boundary: `9999-12-31` and `1000-01-01` are fine; `+020000-01-01`, `275760-09-11`, `+275760-09-12` all poison the row.

The identical bug exists for events: `PATCH /api/events/[eventId]` with `{"dateTime":"+020000-01-01"}` → `app/events/page.tsx:32` (`event.dateTime ? event.dateTime.toISOString() : null` — `Invalid Date` is truthy) throws, taking down `/events`. It also silently breaks reminder scheduling, since `lib/event-reminders.ts` computes `dateTime.getTime()` → `NaN`, so `fireAt.getTime() <= now` is false and no reminder is ever scheduled.

**Impact.** Any club member — no Admin role needed (see HIGH-3) — permanently denies their whole club access to Budget and Events with a single request. **Recovery requires direct database access**: the UI can't render, and the only way to learn the poisoned row's ID is `GET /api/budget/entries`, which also 500s. It's equally a footgun for honest users, since a fat-fingered year in a date field reaches the same state.

**Suggested fix.** Clamp accepted dates to a sane business range (e.g. year 1970–2100) in both validators, and make `serializeEntry` / the events mapper defensive (`Number.isNaN(d.getTime()) ? null : d.toISOString()`) so an already-poisoned row can't take a page down. Consider a `@db.Timestamptz(3)` annotation and a check constraint as defence in depth.

- Delete every budget category and budget entry the club has (`DELETE /api/budget/categories/[categoryId]`, `DELETE /api/budget/entries/[entryId]`), destroying the spend record the union's oversight depends on.
- Submit funding requests to the union in the club's name (`POST /api/budget/request-funding`) — the union sees an official request from the club with no way to tell it wasn't the Admin.
- Submit event approval requests, edit or retitle any event, reassign any task.
- Trigger HIGH-2 against their own club.

`project-overview.md` distinguishes "Club admins — run one approved club day-to-day" from "Club members — the regular participant experience", so today's behaviour contradicts the stated product model. **This one needs a product decision before it's patched**: which of these actions are Admin-only? Budget mutation and funding requests are the obvious candidates; event/task edits are plausibly member-level by design.

**Suggested fix.** Add a `requireClubRole("admin")` helper alongside `getActiveClub()` that reads `orgRole` from `auth()`, and apply it to the routes the product decision selects.

### HIGH-4 — `Club.approvalStatus` is never checked at request time (invariant 3 is not implemented) **[CODE REVIEW]**

`architecture-context.md` invariant 3: *"A club's workspace routes are inert unless `approvalStatus == APPROVED`. This check happens on every workspace route, not just at creation time."* The same requirement appears in the Auth and Access Model section for Liveblocks token issuance.

It is not implemented anywhere. `approvalStatus` appears in only three places in the entire codebase: the approve route that sets it, and two Trigger.dev jobs that filter on it. Neither `getActiveClub()` nor `requireOrgMode("club")` nor `/api/liveblocks-auth` consults it. `Club.approvalStatus` defaults to `PENDING` in the schema.

**Impact.** Latent today — the only code path that creates a `Club` sets `APPROVED` in the same statement, so no non-approved club currently exists (confirmed against the dev database: all 5 clubs are `APPROVED`). But the guard the architecture calls for does not exist, so *any* future path that produces a non-approved club silently grants a fully functional workspace: the reconciliation/backfill flow `architecture-context.md` itself describes, a club-suspension feature, a data migration, or a manual insert. The `PENDING` default means a bare `Club` insert is live immediately. This is a one-line guard today and a breach later.

**Suggested fix.** Have `getActiveClub()` throw (and `requireOrgMode("club")` redirect to a pending/rejected page) unless `approvalStatus === "APPROVED"`, and add the same check to `/api/liveblocks-auth` before issuing a room token.

### MEDIUM-1 — Overspend detection contradicts the club's own budget math **[VERIFIED]**

Two parts of the product compute "is this club overspent?" differently, and they disagree whenever a club records any income:

- Club-facing (`components/budget/budget-summary.tsx:46`): `remaining = availableBudget + income − expenses`.
- Union-facing (`lib/compute-overspend-status.ts:27`): `isOverspent = totalExpenses > availableBudget` — **income is ignored entirely**.

**Reproduction** (verified by running both code paths over the same rows): club with `baselineBudgetAmount = 1000`, one $5,000 INCOME entry, one $5,500 EXPENSE entry. Club's Budget page shows **Remaining: $500** in healthy black. `computeOverspendStatus` returns `isOverspent: true`, and `trigger/check-overspend.ts` raises an `OverspendFlag` that appears on the union's dashboard demanding reconciliation.

**Impact.** Guaranteed false positives for every club that records income (ticket sales, sponsorship, dues) — which is precisely the clubs with the most financial activity. The union chases clubs that are, by the app's own club-side arithmetic, under budget; the club sees a positive balance and can't understand the flag. `project-overview.md` says the system should flag "when tracked spend exceeds everything ever approved for them (baseline + approved requests)", which arguably supports the union-side reading — but then the club-side "Remaining" figure is the wrong number to show. **Needs a product decision on the single definition of "available budget"**, then one shared function used by both sides.

Related: `Club.baselineBudgetAmount` conflates two different things — the baseline set at club approval and the running sum of approved funding requests (`funding/[requestId]/approve/route.ts:45` increments it). There's no way to display "baseline X + approved requests Y", or to audit how a balance got where it is, or to correct a mistaken approval.

### MEDIUM-2 — `lib/get-org-mode.ts` protects no API route; union/club separation on the API surface is incidental **[CODE REVIEW]**

`requireOrgMode()` is used by seven page components and **zero API routes** (verified by grep). API routes call `getActiveClub()` or `getActiveInstitution()` directly, and those two helpers each query only their own table — neither checks that the active org *isn't* also the other kind.

In practice a union org has no `Club` row and a club org has no `UnionStaffOrgLink`, so cross-mode API access fails today. But that safety is a property of the data, not an enforced invariant. If one `clerkOrgId` ever ends up in both tables (operator error in `scripts/setup-union-staff-test-org.ts`, a future self-serve union signup, a botched migration), `getOrgMode()` resolves it as `union` and hides the club chrome — while every club API route continues to serve that org fully. The mode boundary the architecture describes would then exist only in the UI.

**Suggested fix.** Make the exclusivity explicit: have `getActiveClub()` fail if the active org is also a Union Staff org and vice versa, or route all API handlers through `requireOrgMode`. Add a DB-level guard against an org ID appearing in both tables.

### MEDIUM-3 — Receipt uploads have no size, count, or type limit **[CODE REVIEW]**

`app/api/budget/entries/[entryId]/receipts/route.ts` accepts every `File` in the `files` field with no cap on file size, file count, or per-club total. Any club member can upload arbitrarily large files, repeatedly, to any number of entries they create. Path traversal itself *is* handled correctly — `safeFileName()` strips directory components and leading dots, and the download route's `/^[a-zA-Z0-9._-]+$/` filename check plus the `receiptUrls.some(url => url.endsWith(pathname))` ownership check together make a traversal or cross-club read infeasible (reviewed specifically; no bypass found). The gap is purely resource limits. **Suggested fix:** cap file size (~10 MB), cap files per entry, and cap receipts per club; enforce the type allowlist from HIGH-1 in the same place.

### MEDIUM-4 — Money amounts accept non-money values **[VERIFIED]**

`parseEntryCreateBody` (and the funding/category equivalents) validate with `Number(x)` + `Number.isFinite(x)` + `> 0`. Verified accepted values and what they become:

| Sent | Stored as |
|---|---|
| `true` | `$1.00` |
| `[5]` | `$5.00` |
| `"0x10"` | `$16.00` |
| `" 42 "` | `$42.00` |
| `"1e308"` | `1e+308` |
| `1e20` | `$100,000,000,000,000,000,000.00` |
| `0.005` | sub-cent value that rounds in display but not in the DB |

`Decimal` is declared with no precision/scale (`prisma/models/budget.prisma`), so Postgres accepts unbounded values, and every read goes through `Number()` (`lib/budget-serialize.ts`, `lib/compute-overspend-status.ts`), converting exact decimals to IEEE-754 doubles. Client-side totals (`sumEntries`) then accumulate float error across entries.

**Impact.** Mostly data-quality rather than exploitable: a club member can poison their union's dashboard with a $1e20 expense, and sub-cent amounts make displayed totals disagree with stored totals. **Suggested fix:** require `typeof x === "number"`, round/validate to 2 decimal places, impose a sane maximum, declare `@db.Decimal(12, 2)`, and keep money as `Decimal` (or integer cents) end-to-end rather than round-tripping through `Number()`.

### MEDIUM-5 — The public club-application endpoint is unhardened **[CODE REVIEW]**

`POST /api/institutions/[institutionSlug]/applications` is reachable by any signed-in user with no organization (`proxy.ts` `NO_ORG_REQUIRED_PATHS`). Issues, in order of severity:

- **No rate limiting.** Any signed-in user can submit unlimited applications to any institution, flooding that union's approval queue. Each submission also triggers `getOrSeedFormSchema`, which performs an `upsert` (a write) on every call.
- **`proposedAdminEmail` is unvalidated free text.** It's declared `TEXT` in the default schema and `validateFormAnswers` only checks `typeof value === "string"`. On approval it is passed straight to Clerk's `createOrganizationInvitation`. A malformed address makes the approval fail *after* the application has been claimed — the revert path at `approve/route.ts:174` handles that correctly, but the union just sees a generic 500. Worse, an applicant can name **any** email as the incoming club admin; nothing verifies they control it, so the union is one careless approval away from making an arbitrary third party a club admin.
- **`await request.json()` is unguarded** (line 53). Malformed JSON throws → generic 500 instead of 400. Same at `app/api/union/forms/[formType]/route.ts:126`. Every other route in the app wraps this correctly.
- **Institution slugs are enumerable** — `/apply/<slug>` renders a page (leaking the institution's real name) for a valid slug and an error for an invalid one, letting anyone enumerate which universities are customers.

**Suggested fix.** Rate-limit per user and per institution; validate the email with a real format check before storing; wrap the JSON parse; make `getOrSeedFormSchema` read-only on this path.

### MEDIUM-6 — No length limit on any free-text field **[VERIFIED]**

No field anywhere validates maximum length — not `validateFormAnswers` (which only checks type and required-ness), not the budget `note`, event `title`/`description`/`location`, task `title`, or brainstorm idea `text`. Verified: a 2,000,000-character `note` was accepted and stored without complaint. Multiplied across the unlimited application submissions in MEDIUM-5, this is a cheap way to bloat the database and slow down every page that renders the affected rows. **Suggested fix:** enforce per-type maximums in `validateFormAnswers` and in each route's parser, and add `@db.VarChar(n)` where appropriate.

### LOW-1 — `check-overspend` job is not concurrency-safe and aborts on first failure **[VERIFIED]**

`trigger/check-overspend.ts` upserts `OverspendFlag` on the unique `openKey`. Verified: 24 concurrent upserts on the same key → 15 succeeded, **9 threw `P2002`** (unique constraint violation). Prisma's `upsert` is not atomic against a concurrent insert on a unique column. Within a single run the loop is sequential so this can't fire, but two overlapping runs (a Trigger.dev retry overlapping the daily schedule) would. Compounding it, the loop has **no per-club `try`/`catch`** — unlike `trigger/send-weekly-digest.ts:30`, which correctly isolates each club — so one throw aborts the run and every club after it in the list is silently never checked. **Suggested fix:** catch `P2002` and treat it as success, and wrap each club iteration in `try`/`catch` matching the digest job.

### LOW-2 — A union can delete reserved form fields via the API and break its own approvals **[CODE REVIEW]**

`parseFields` in `app/api/union/forms/[formType]/route.ts` validates field shape but never enforces that reserved fields survive. `getOrSeedFormSchema` re-inserts `club_name`, `eventName`, and `amount` on next read, but **not** `proposedAdminEmail`. Removing that one makes every subsequent application silently fall back to the submitter's own Clerk email as the proposed club admin (`applications/route.ts:76-82`) — a `console.warn` and nothing user-visible. `parseFields` also accepts empty-string and duplicate `fieldKey`s, and `fieldKey: "__proto__"` (harmless as written, since `pickAnswers` assigns to a fresh object literal, but worth blocking). **Suggested fix:** reject any schema save that drops a reserved field, and validate `fieldKey` against `/^[a-zA-Z0-9_]{1,64}$/` plus a uniqueness check.

### LOW-3 — `getOrSeedFormSchema` silently rewrites a union's saved schema on read **[CODE REVIEW]**

`ensureReserved` (`lib/form-schema-defaults.ts:180-196`) resets a reserved field's `label` back to the canonical default whenever its `type` or `required` differs, and persists that with a `formSchema.update`. A union that renames "Club name" to "Society name" and makes it optional gets both changes reverted the next time anyone loads the form — with no notification. It also means a **read** path performs a write on every call, from an endpoint anyone signed-in can hit (MEDIUM-5). This contradicts the "a union can relabel fields" promise in `project-overview.md`. **Suggested fix:** normalize `type`/`required` only, never `label`; move the whole normalization to schema-save time rather than read time.

### LOW-4 — Stale duplicate files are committed to git **[VERIFIED]**

`lib/form-schema-defaults 2.ts` and `app/api/events/request-approval/route 2.ts` are both tracked. The route duplicate is inert (Next only routes `route.ts`) but is an older copy missing the JSON-parse guard; the lib duplicate is a stale copy of the reserved-key constants that the real approve routes depend on. Both are a live drift hazard — an editor jumping to the wrong file, or a future refactor picking up the wrong constants, silently breaks approvals. **Suggested fix:** delete both.

### LOW-5 — API routes redirect to HTML sign-in instead of returning 401 JSON **[VERIFIED]**

Verified against the running dev server: unauthenticated `GET /api/budget/entries`, `POST /api/liveblocks-auth`, and every other API route return **`307` to `/sign-in?redirect_url=...`**, not `401`. Access is correctly denied, so this isn't a hole — but any client `fetch()` follows the redirect, receives an HTML page, and fails with a JSON parse error rather than a clean auth failure. That makes real expired-session behaviour in production look like a random client crash. **Suggested fix:** in `proxy.ts`, return `401` JSON for `/api/*` and redirect only for page routes.

### LOW-6 — `app/page.tsx` is a leftover chrome-preview demo at the app root **[CODE REVIEW]**

`/` is a client component rendering "App Chrome Preview" with a hardcoded `mode="club"` sidebar and an example dialog. It has no auth or org-mode check of its own beyond the middleware's signed-in requirement, so a Union Staff user landing on `/` gets club chrome. **Suggested fix:** redirect `/` to `/team` or `/union/applications` based on `getOrgMode()`.

### LOW-7 — Receipt blob paths are guessable and overwritable within a club **[CODE REVIEW]**

Receipts are stored at the deterministic path `receipts/{clubId}/{entryId}/{filename}` with `allowOverwrite: true` in a **public** Blob store. Cross-club access is prevented by the authenticated download route (and the raw URL is deliberately never sent to the client — `serializeEntry` emits only filenames). But the underlying blob is publicly readable to anyone who learns or guesses the URL, and any club member can overwrite another member's receipt by uploading a file with the same name to the same entry — replacing financial evidence with no audit trail. The existing Open Questions entry already records that the store is public-only because of Vercel provisioning; this notes the overwrite consequence specifically. **Suggested fix:** add a random suffix to blob pathnames (keeping the DB as the only index), and reprovision as a private store when the production store is created for 23-deployment.md.

## Resolved Decisions

- Club URLs are slug-based (`/[clubSlug]/events`, etc.) — chosen for shareable/bookmarkable links over a slug-free session-only approach.
- Platform supports many universities; each institution's union and clubs are fully isolated from every other institution.
- Club creation is never self-serve — it always goes through a `ClubApplication` reviewed by the union, approving the club and its proposed admin in a single decision.
- Event approval and funding approval are separate queues/workflows; funding is reviewed at the headline amount only, not itemized.
- Clubs have both a baseline budget (set at club approval time) and can submit one-off funding requests on top of it.
- Union-oversight features (applications, event approval, funding, overspend flags) are being built before Events board / Brainstorm canvas, since that's the part a union would actually pay for.

## Architecture Decisions

- Multi-tenant via Clerk Organizations — one org per club. No local roles table; Admin/Member maps directly to Clerk org roles.
- Liveblocks scoped to exactly two surfaces: Events board and Brainstorm canvas. No real-time elsewhere.
- Brainstorm canvas persists as a Vercel Blob snapshot (`brainstorm/{clubId}.json`); everything else lives directly in Postgres via Prisma.
- Budget tracking is full-depth: categories, per-event linking, running totals, simple report view (not a minimal expense log).
- No AI-generation features in this app — out of scope, unlike the reference project this workflow was adapted from.
